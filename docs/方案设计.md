# McpHub 桥接器设计方案

> 状态：待评审 · 版本 v0.1 · 2026-11-19
> 定位：**对上只占一份 MCP 配置，对下动态管理一组按项目绑定的子 MCP。**

---

## 1. 问题与目标

### 1.1 现状痛点

- Agent 工具只有**一份全局 MCP 配置**，不支持项目级 MCP。
- 多个项目共用同一份配置，导致所有 MCP 的启动参数/env 是固定的。
- 部分 MCP 必须绑定项目或文件才有意义：
  - **sqlite MCP**：参数里写死某个 `.db` 路径，切项目后仍指向旧库。
  - **aoci MCP**：需要通过 env/参数拿到当前项目根目录，切项目后上下文错位。
- 直接后果：切项目 → 这些 MCP 失效或操作错项目，且无法在同一会话里并行操作两个项目的同类 MCP。

### 1.2 目标

1. Agent 侧**只需注册 McpHub 一个 MCP**，之后不再改全局配置。
2. 支持 MCP 的**安装 / 查询 / 修改 / 删除 / 重启**全生命周期管理。
3. 支持**代理执行**：把工具调用路由到目标子 MCP，并把结果原样带回。
4. 核心能力：**按项目绑定 + 实例隔离**——同一子 MCP 在不同项目下用不同参数、跑不同进程实例，互不干扰。
5. 切换项目不需要重启 Agent，也不需要改任何全局配置。

### 1.3 非目标（v1 不做）

- 不做权限系统 / 多用户隔离（本机单用户工具）。
- 不做 MCP  markets 自动发现与下载（安装靠用户提供 command/args）。
- 不改 Agent 本身。

---

## 2. 核心思路

引入一个**桥接层（Bridge / Hub）**，把"一份全局配置"和"多项目上下文"之间的矛盾收口到自身内部：

- **对上（面向 Agent）**：McpHub 是一个标准 MCP Server（默认 stdio），暴露一组固定的**元工具（meta tools）**。Agent 只认这一份配置。
- **对下（面向子 MCP）**：McpHub 是一个 MCP Client 管理器，按需启动、连接、缓存、回收子 MCP 实例（stdio / SSE / Streamable HTTP）。
- **关键机制**：每次代理调用都携带 `project` 上下文；McpHub 用它渲染子 MCP 的**绑定模板**（如 `${PROJECT_ROOT}/data/app.db`），用渲染结果作为**实例 Key** 做隔离与复用。

这样，项目差异从"配置文件里的固定值"变成了"调用时的动态参数"，而 Agent 侧配置永远不变。

## 3. 架构

### 3.1 分层

```
┌─────────────────────────────────────────────────────────┐
│ Agent（只有一份全局 MCP 配置）                          │
│   mcp.json: { "mcp-hub": { command: "python -m mcp_hub" } }│
└───────────────────────┬─────────────────────────────────┘
                        │  MCP 协议（stdio）
┌───────────────────────▼─────────────────────────────────┐
│ McpHub（对上 Server / 对下 Client 管理器）               │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌────────────┐  │
│  │ 元工具层  │ │ 路由分发  │ │ 绑定引擎  │ │ 实例管理器  │  │
│  │ tools    │ │ Router   │ │ Bindings │ │ Manager    │  │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘ └─────┬──────┘  │
│       └────────────┴────────────┴─────────────┘          │
│  ┌──────────────────────────────────────────────────┐    │
│  │ 配置层：hub.json（全局） + <project>/.mcp-hub.json │   │
│  └──────────────────────────────────────────────────┘    │
└───────────────────────┬─────────────────────────────────┘
                        │  子 MCP 协议
┌───────────────────────▼─────────────────────────────────┐
│ 子 MCP 实例池（按 project 隔离，惰性创建）              │
│  sqlite@projA  sqlite@projB  aoci@projA  aoci@projB ... │
└─────────────────────────────────────────────────────────┘
```

### 3.2 组件职责

| 组件 | 职责 |
|---|---|
| `server.py` | 对上 MCP Server，定义元工具，做参数校验与结构化返回 |
| `router.py` | 解析 `mcp` + `tool` + `project`，决定目标实例 |
| `bindings.py` | 加载配置、渲染 `${VAR}` 模板、计算实例 Key |
| `manager.py` | 实例生命周期：惰性启动、复用、重启、LRU 淘汰、空闲回收 |
| `client.py` | 对下 MCP Client 封装（stdio / SSE / HTTP），维护长连接 session |
| `config.py` | 配置模型（pydantic）、全局/项目级配置加载与合并 |
| `errors.py` | 统一错误码与结构化错误返回 |

## 4. 项目绑定机制（核心）

### 4.1 绑定策略

每个子 MCP 在注册时声明 `bindings.strategy`：

| 策略 | 含义 | 实例 Key | 适用场景 |
|---|---|---|---|
| `global` | 不随项目变化，所有项目共享一个实例 | `__global__` | 纯工具型 MCP（如 fetch、time） |
| `per_project` | 每个项目独立实例，模板按项目渲染 | `<mcp>:<project_root>` | sqlite、aoci 等绑定型 MCP |
| `per_file` | 按绑定到的具体文件隔离（可从调用参数推断） | `<mcp>:<resolved_file>` | 同一项目内操作多个 db/文件 |

### 4.2 模板变量

在 `args` / `env` / `cwd` 中支持以下占位符，调用时由 `project` 上下文渲染：

| 变量 | 含义 |
|---|---|
| `${PROJECT_ROOT}` | 项目根目录（绝对路径） |
| `${PROJECT_NAME}` | 项目目录名 |
| `${PROJECT_ID}` | 项目标识（默认取 root 的短 hash，可覆盖） |
| `${CWD}` | 调用方传入的工作目录（未传则等于 PROJECT_ROOT） |
| `${HOME}` | 用户主目录 |
| `${ENV:NAME}` | 读取环境变量 |

渲染时若必填变量缺失（如未传 project 而模板需要 `${PROJECT_ROOT}`），直接返回结构化错误，**不静默使用旧值**——这正是解决"切项目后仍指向旧路径"的关键。

### 4.3 项目级叠加配置（重要）

McpHub 自己支持项目级覆盖，不依赖 Agent：

- 全局：`~/.mcp-hub/hub.json`（通过 `MCPHUB_CONFIG` 可覆盖路径）
- 项目级：`<project_root>/.mcp-hub.json`（可选）

当调用带 `project` 时，McpHub 自动加载并**浅合并**项目级配置到全局配置之上，典型用途：

```json
{
  "bindings": {
    "sqlite": {
      "db_file": "data/local.db"
    }
  }
}
```

即：全局定义"sqlite MCP 怎么启动"，项目级定义"这个项目用哪个 db"。切项目零配置、零重启。

### 4.4 示例

> 实施说明：下列 sqlite 示例中的 npm 包 `@modelcontextprotocol/server-sqlite` 已下架，最终实现以 filesystem 作为默认示例（见 README）。此处的 sqlite 仅作 per_project 绑定方式的示意。

**sqlite MCP（per_project）**

```json
{
  "name": "sqlite",
  "type": "stdio",
  "command": "npx",
  "args": ["-y", "@modelcontextprotocol/server-sqlite", "${PROJECT_ROOT}/data/app.db"],
  "env": {},
  "bindings": {
    "strategy": "per_project",
    "required": ["PROJECT_ROOT"]
  },
  "enabled": true
}
```

**aoci MCP（per_project，通过 env 传项目根）**

```json
{
  "name": "aoci",
  "type": "stdio",
  "command": "aoci-mcp",
  "args": [],
  "env": { "AOCI_PROJECT": "${PROJECT_ROOT}" },
  "cwd": "${PROJECT_ROOT}",
  "bindings": {
    "strategy": "per_project",
    "required": ["PROJECT_ROOT"]
  },
  "enabled": true
}
```

> aoci MCP 的真实启动命令与参数需要在开工前确认（见第 10 节），上面是结构示例。

## 5. 对外工具 API（MCP tools）

### 5.1 协议层关键决策：元工具代理 vs 动态聚合

标准 MCP 的 `tools/list` 是静态的，而子 MCP 的工具需在连接后才能得知、且随项目变化。两种方案：

- **方案 A（推荐，v1 默认）：元工具代理。** McpHub 只暴露固定元工具，Agent 通过 `mcp_call(mcp, tool, args, project)` 调用。优点：配置一次、稳定、工具名不冲突、子 MCP 未启动也能管理。缺点：Agent 需多一步"先查工具再调用"。
- **方案 B（可选增强）：动态聚合。** 在 `tools/list` 时连接所有启用子 MCP，聚合并加前缀 `hub_<mcp>_<tool>`。更原生，但工具数膨胀、命名冲突、每次列举都要连子 MCP。

v1 采用方案 A，预留方案 B 的开关。

### 5.2 元工具清单

| 工具 | 作用 | 主要参数 |
|---|---|---|
| `mcp_list` | 列出子 MCP 及运行状态 | — |
| `mcp_get` | 查看某个子 MCP 配置 | `name` |
| `mcp_install` | 注册/安装子 MCP | `name, type, command, args, env, cwd, bindings` |
| `mcp_update` | 修改子 MCP 配置 | `name` + 待改字段 |
| `mcp_remove` | 卸载子 MCP | `name` |
| `mcp_restart` | 重启（终止全部实例，下次惰性重建） | `name` |
| `mcp_set_context` | 设置默认项目上下文 | `project` |
| `mcp_tools` | 发现某个子 MCP 的工具列表 | `name, project` |
| `mcp_call` | **代理执行**目标工具 | `mcp, tool, args, project?` |

### 5.3 核心签名示例

```python
# 查询
mcp_list() -> {
  "ok": true,
  "mcps": [
    {"name": "sqlite", "enabled": true, "instances": 2, "status": "running"},
    {"name": "aoci",   "enabled": true, "instances": 1, "status": "running"}
  ]
}

# 发现工具（惰性连接对应项目的实例）
mcp_tools(name="sqlite", project="D:/work/proj-b")
  -> {"ok": true, "tools": [{"name": "query", "inputSchema": {...}}, ...]}

# 代理执行（核心）
mcp_call(
  mcp="sqlite",
  tool="query",
  args={"sql": "select count(*) from users"},
  project="D:/work/proj-b"
) -> {"ok": true, "result": {...}, "instance": "sqlite:D:/work/proj-b"}
```

**调用时序**

1. Agent 调 `mcp_call(mcp, tool, args, project)`。
2. `mcp_set_context` 设置的默认项目在 `project` 省略时兜底；两者都无且模板需要项目 → 报错。
3. `bindings` 用 `project` 渲染 `args/env/cwd`，计算 `instance_key`。
4. `manager` 查池：命中则复用；未命中则启动进程 → 建立 ClientSession → `initialize` → 缓存。
5. 在该实例的 session 上执行 `tools/call(tool, args)`，结果原样返回。
6. 更新 `last_used`，交给空闲回收器管理。

### 5.4 结构化错误

```json
{
  "ok": false,
  "error": {
    "code": "PROJECT_REQUIRED",
    "message": "mcp 'sqlite' requires project context (${PROJECT_ROOT})",
    "mcp": "sqlite",
    "tool": "query"
  }
}
```

常见错误码：`NOT_FOUND` / `DISABLED` / `PROJECT_REQUIRED` / `TOOL_NOT_FOUND` / `START_FAILED` / `TIMEOUT` / `CALL_FAILED`。

## 6. 子 MCP 生命周期管理

- **惰性启动**：首次 `mcp_call` / `mcp_tools` 才启动进程，避免全局配置里一堆用不到的 MCP 常驻。
- **实例隔离**：`instance_key = f"{mcp}:{project_root}"`（`per_project`）或 `f"{mcp}:{resolved_file}"`（`per_file`）；`global` 策略固定 `__global__`。
- **并发安全**：每个实例内部用 `asyncio.Lock` 串行化请求；不同实例之间并行。
- **空闲回收**：后台任务按 `idle_timeout`（默认 30 分钟）关闭闲置实例并释放子进程。
- **容量上限**：`max_instances`（默认 16）超出时按 LRU 淘汰最久未用实例。
- **崩溃自愈**：session 断开时先尝试自动重启一次，仍失败则返回 `CALL_FAILED`。
- **重启语义**：`mcp_restart(name)` 终止该 MCP 的全部实例并清空工具缓存，下次调用按最新配置重建。

## 7. 配置格式

`~/.mcp-hub/hub.json`：

```json
{
  "version": 1,
  "defaults": {
    "idle_timeout_minutes": 30,
    "max_instances": 16,
    "call_timeout_seconds": 60,
    "default_project": null
  },
  "mcps": {
    "sqlite": { "...": "见 4.4" },
    "aoci":   { "...": "见 4.4" }
  }
}
```

项目级 `<project_root>/.mcp-hub.json` 只需写差异项（见 4.3）。配置文件变更由 `mcp_install/update/remove` 落盘，不手写也可全部通过工具管理。

## 8. 技术选型与目录结构

- **语言**：Python 3.11+（工作区即 Python 项目）
- **协议库**：`mcp` 官方 Python SDK —— `FastMCP` 做对上 Server；`ClientSession` + `stdio_client` / `sse_client` / `streamablehttp_client` 做对下 Client
- **配置模型**：`pydantic v2`
- **并发**：`asyncio`（锁、后台回收任务）

```
McpHub/
  mcp_hub/
    __init__.py
    server.py        # 对上 MCP Server + 元工具
    router.py        # 路由分发
    bindings.py      # 模板渲染 + 实例 Key
    manager.py       # 实例池 / 生命周期
    client.py        # 对下 Client 封装
    config.py        # 配置模型与加载/合并
    errors.py        # 错误码
  config/
    hub.example.json # 示例配置
  tests/
  docs/
    方案设计.md      # 本文档
  pyproject.toml
  README.md
```

Agent 侧全局配置只加一条：

```json
{
  "mcpServers": {
    "mcp-hub": {
      "command": "python",
      "args": ["-m", "mcp_hub"],
      "env": { "MCPHUB_CONFIG": "C:/Users/Admin/.mcp-hub/hub.json" }
    }
  }
}
```

## 9. 分阶段实施

1. **阶段 1 · 骨架与管理面**：配置模型 + 全局/项目级加载、`mcp_list/get/install/update/remove/set_context/restart`、stdio 子 MCP 连接与 `initialize`。
2. **阶段 2 · 代理执行与绑定**：`bindings` 模板渲染、`instance_key` 隔离、`mcp_call` / `mcp_tools`、实例池惰性创建。
3. **阶段 3 · 协议扩展**：SSE / Streamable HTTP 子 MCP 支持；可选的动态工具聚合模式（方案 B）。
4. **阶段 4 · 健壮性**：超时、崩溃自愈、LRU/空闲回收、结构化日志、单元测试与端到端验证。

阶段 1+2 即可解决当前"切项目失效"的核心问题，可先交付验证再迭代。
